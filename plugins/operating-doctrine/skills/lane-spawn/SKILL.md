A detour is any work item that surfaces inside a lane but is not that lane's job per its kickoff. Quick verification reads (a file check, a live probe) are not detours; do those inline. Anything with its own state, its own carry-backs, or its own rulings is a detour and spawns.

## The spawn pair

When a detour fires, one message ships up to three parts, in this order.

PASTE 1 -- LANE KICKOFF (always). A fenced block Allison pastes as the FIRST message of a new conversation. Tell her, outside the block, exactly where: which Claude project, which SURFACE (a chat conversation in the Claude app or Cowork, or a Claude Code session), and the name to give it. The block contains, in this order:

- **First line: the conversation name, plain and alone.** Nothing else on that line, nothing above it. See the next section for why this is first and why it is bare.
- Then the envelope: `CONVERSATION: {Claude project} / {conversation name}` and `SURFACE: {chat conversation | Claude Code session}` and, when a worker session exists or will exist, `WORKER SESSION: {exact Code session name}`.
- Then the mission contract, two lines, whenever this lane is a mission table (v1.7): `MISSION:` what this table exists to accomplish, in one sentence, and `DONE WHEN:` the evidence that proves that mission achieved. See "The mission contract" below for what makes a good DONE WHEN and when the two lines are correctly omitted.
- What this lane is: its one job, in two or three sentences.
- Why it exists: what happened in the origin lane that spawned it.
- Standing state it inherits: only the rulings and facts it needs, never the origin lane's whole queue.
- Its only jobs, and an explicit do-not-absorb list naming the origin lane and any adjacent lanes.
- First move: what to do when its first input (usually a Code carry-back) arrives.
- Return path: what short finding, if any, comes back to the origin lane, and that Allison carries it as a paste.

Shape of a chat kickoff, top of block:

```
Ember Rail Repair

CONVERSATION: Aura: Strategic Advisor / Ember Rail Repair
SURFACE: chat conversation (Claude app)
WORKER SESSION: Ember Rail Repair - Rail Diagnostic
MISSION: Restore the Ember briefing rail so the 8 AM briefing sends on its own.
DONE WHEN: Two consecutive briefings send unattended and land on Allison's phone, verified from delivery logs.

WHAT THIS LANE IS: ...
```

The name appears twice on purpose. Line one is for the auto-titler, which reads the message and cannot be told anything. The CONVERSATION line is for the receiving Claude, which needs the project as well as the name.

PASTE 2 -- CODE BLOCK (only when a worker session is needed). Per the code-block-routing skill, with one requirement specific to spawning: its `CLAUDE HOME` names the NEW lane, never the origin lane. The carry-back must land where the work will be ruled. The Code half keeps `SESSION NAME`, keeps its first-contact self-title-and-verify instruction, and carries its `WORKTREE` line naming the isolated worktree the worker creates from a freshly fetched remote ref and confirms by absolute path at first contact (v1.3, per code-block-routing's Worktree Isolation); none of the chat rules touch it. Under v1.4 the worker name is `<Table Name> - <Specific Job>` and the worker titles itself on Desktop, so no `claude -n` launch line rides unless the target is a CLI-only launch.

RESUME LINE (always, same message, after the blocks). One line stating what the origin lane awaits from the new lane (or 'nothing, fully detached'), then the origin lane's next step, immediately. The origin lane never closes its turn on the detour.

## The conversation name is the first line (v1.2)

Chat conversation titles cannot be set programmatically. The Claude app and Cowork auto-title a conversation from its first message, and no session, tool, or API can override that (live-verified 2026-08-03, reconfirmed by the 2026-08-07 failure below). The only lever the block-writer has is what the first message says first.

So: **the conversation name is the literal first line of the kickoff block, plain and alone.** No label in front of it, no date suffix, no mission text above it, no envelope line above it. Lead with the name and the auto-titler lands on it or close to it.

The failure this replaces, 2026-08-07: a spawn block buried the conversation name several lines down and opened with mission text instead. The app titled the chat off the mission, and the lane had two names from birth, the one the ledger recorded and the one Allison could see.

**Chat lane identity is the kickoff header line**, per the standing 2026-08-03 ruling; the displayed title is not the mechanism, because it cannot be set programmatically. Leading with the name is what gives the auto-titler the right material.

**Table Birth (v1.4, decision 0074) replaces near-match acceptance for tables.** A spawned conversation is seated as the authoritative chair of a new table (decisions 0081 and 0088), and a table is named exactly once, at birth. Mechanics:

1. The kickoff block leads with the bare name (above), so the auto-titler lands on it or close.
2. At deliberate Table Birth the receiving chair DECLARES identity in two lines (v1.5, decision 0077, trigger amended by decisions 0082 and 0084): `ROOM: <exact room identity>` then `TABLE NAME: <exact table name>`. Birth is a deliberate declared act, never an automatic consequence of a first substantive turn, and a conversation that has not performed it is Scratch. The ROOM string comes solely from the room's own Project Instructions ROOM identity literal, which the table registry consumes, validates, carries, and points at but never silently replaces, and the installed literal wins on any disagreement with the disagreement surfaced. Bridge until cutover, decision 0082: the installed automatic birth-declaration wiring continues to bind until Allison rules the cutover, as a pre-cutover act a chair performs on behalf of its table.
3. The surface cannot read its own visible title, so it states the intended TABLE NAME, says plainly that visible-title parity cannot be verified from that surface, and hands Allison the exact required chair title, the bare TABLE NAME, if the visible title differs. Chair title parity is continuing (v1.8, decision 0088). The same exact title is handed to her again at Rejoin, at Reseat, and whenever drift is actually observed or reported, never on a schedule and never as an unprompted nag, and a surface that can read and set its own title maintains parity itself. The platform-honesty rule stands, never claiming a title was inspected, matched, or fixed when the surface cannot know that (v1.5, decision 0077).
4. After that the table name is stable for the table's life, and no implementation dispatch leaves an unnamed or unconfirmed table. A Scratch conversation dispatches nothing and owns nothing, and no chair acquires table authority by asserting it, only through Birth, Rejoin, or Reseat (decision 0081). A worker dispatched from the table is not a chair and never acquires chair authority by executing (decision 0088).
5. A mission table's Birth declaration carries two more lines below the name (v1.7), `MISSION:` and `DONE WHEN:`, taken verbatim from the kickoff block when one shipped and composed by the chair when the table was born some other way. They are declared once, at Birth, alongside the name. A table born without them can never self-surface its own completion, which is the whole failure v1.7 exists to kill.

What did NOT come back: routine, repeated, or unprompted chat rename requests stay banned, `/rename` is still never handed out for a chat in any form, and chat lanes still never get PARITY MISMATCH flags. Table Birth is a single naming act at the moment a table is created, not a maintenance loop, and the NAME is set there once. What v1.8 changes under decision 0088 is the title mirror, not the name. The birth-only limit on raising a chair title correction is superseded, because the visible chair title must read exactly the TABLE NAME for the chair's whole life, so the correction is raised at Birth, at Rejoin, at Reseat, and whenever drift is actually observed or reported. A title mismatch never changes the table's identity, the title is repaired back to the table. A manual visible-title rename alone, Allison's own included, never changes the TABLE NAME, the table's identity, or the ledger's record of it, so the ledger never follows a retitled sidebar. If the visible chair title differs from the TABLE NAME, that is title drift, and it is repaired back to the exact TABLE NAME under decision 0088. A genuinely different durable mission gets a different table by deliberate Birth, never by renaming a sidebar title.

## The mission contract: MISSION and DONE WHEN (v1.7)

A mission table exists to accomplish a stated thing. The contract is the two lines that say what that thing is and how anyone will know it happened, and it is written once, at Birth, into the table's own durable record.

`MISSION:` one sentence naming what this table exists to accomplish. Allison's stated outcome, not the build. "Restore the Ember briefing rail so the 8 AM briefing sends on its own," never "edit the launchd plist."

`DONE WHEN:` the acceptance evidence that proves the mission achieved. It must be something a later reader can check without asking Allison, so it names artifacts, merges, live behavior, or delivery proof. "Two consecutive briefings send unattended and land on Allison's phone, verified from delivery logs" is a DONE WHEN. "The rail works" is not, because nothing can be checked against it. When the honest completion condition is Allison's own acceptance of a deliverable, say that exactly, naming the deliverable she accepts, so the check has one real thing to look for.

Which tables carry it, and which correctly do not. Every mission table carries it, meaning any table born to accomplish a stated outcome, whether it dispatches workers or not. A Scratch or general-purpose conversation carries neither line and is exempt: it is thinking, reading, exploring, or keeping Allison company on a subject, it holds no table identity under decision 0081, and it is never nagged to archive merely because a topic ended. A standing-subject table under decision 0066, one that exists to be there rather than to finish, is exempt the same way and says so plainly in place of a DONE WHEN, so the exemption is a recorded fact rather than a missing line. Absence of the contract is never treated as an unfinished table.

What reads it. The session-wrap terminality check (session-wrap v1.11, section 0A) reads this contract when acceptance evidence lands and decides whether the mission is achieved. That is the whole point of writing it at Birth: the table proves its own completion from its own record, so Allison never has to be the one who notices the work is over.

What it is not. It is not a plan, a scope, a task list, or a success metric, and it never grows as the work goes. A mission that genuinely changed is Allison's ruling to make, and a completed table never rewrites its own DONE WHEN to keep itself alive (session-wrap v1.11, section 4B).

Pre-cutover boundary. The contract rides on the birth declaration wiring installed today, which decision 0082's bridge clause keeps binding until Allison rules the one cutover. It creates no registry, no registrar record, and no routing-state write.

**The worker half (v1.4, concurrency amended v1.6, boundary v1.8).** A worker is a temporary execution session dispatched from the table into an approved implementation engine. It is not a chair, even though Claude Code presents it as a session. The chair stays home at the table while the worker executes, and the worker returns its evidence to the table's chair before following its own terminal lifecycle (decision 0088). Worker admission is registrar-governed by exact execution scope (decision 0082): a table may hold multiple active workers whose exact scopes do not conflict, and a duplicate same-table same-title worker or an exact scope collision is refused. If a detour genuinely needs its own separable implementation, giving it its own table is still the cleanest move, and a spawn pair is exactly what produces one. Bridge until cutover: the registrar does not exist yet, so until Allison rules the cutover the installed one-active-worker practice continues to bind and a second concurrent implementation job still gets its own exactly named table first. Worker naming and self-titling live in code-block-routing, Session Naming; classification, drift repair, and the registration and scope-collision check live in the session-steward skill.

## Vocabulary lock: CONVERSATION for chats, SESSION for Code (v1.2)

The two surfaces get two words, and they never trade.

- A block bound for a **chat conversation** (Claude app or Cowork) heads its envelope `CONVERSATION:`. A chat block carrying a `SESSION:` line is **malformed**: rewrite it before it ships.
- A block bound for a **Claude Code session** heads its envelope `SESSION:`, per the pin skill and code-block-routing. That is unchanged.
- `WORKER SESSION:` inside a chat kickoff is correct and is not a violation. It names the Code lane the chat will receive carry-backs from; it is a pointer, not the block's own header.
- `CLAUDE HOME:` inside a Code block still names the Claude project plus conversation. That is a pointer too, and it is unchanged.

One word per surface, so a block's destination is legible from its first envelope line even when it lands somewhere unexpected.

## Every paste carries the envelope (v1.1)

A misroute in live use (2026-08-03) proved that any paste without identity lines strands the receiving session in the first-contact question. So the rule extends beyond Code blocks: EVERY paste handed to Allison that is bound for another lane or session, kickoffs, directives, envelope confirmations, carry-notes, everything, opens with lines that name the destination lane and, where known, the session. A paste that could land anywhere must be able to identify itself anywhere. The pastes are the nervous system; unlabeled pastes are how lanes fall off.

Under v1.2 a chat kickoff satisfies this with its first line (the bare conversation name) plus its `CONVERSATION:` line immediately below. The bare name does not replace the envelope; it sits above it.

## Landing on the wrong door (v1.6, inspect before adopt)

Chat conversations and Claude Code sessions look nearly identical to a human mid-flow, and rooms look alike in a sidebar. Misroutes will happen. The v1.1 rule said the receiving surface ADOPTS a fully named block. That rule is retired by decision 0081's chair authority law, because adoption is how a wrong door quietly becomes a second identity for work it does not own.

The rule for the RECEIVING surface. Read the envelope first, before executing anything. If the block names a destination that is not this surface, this room, or this table, INSPECT it, REFUSE it, and state the correct routing plainly, naming the exact room, table, or session it belongs to. Do not execute the brief. Do not declare Birth from it. Do not write anything durable under the inbound identity. Do not claim the identity the block carries. Say what the block appears to be for, so Allison can carry it to the right door in one move.

A refusal is the correct, successful behavior, not a failure and not an obstruction. The proof it works is live, 2026-08-30: this table's authoritative birth packet was misdelivered to NORTH, NORTH refused it and stated the correct routing, and that refusal is preserved as a positive acceptance fixture at aura intake/2026-08-30-wrong-door-refusal-example-routing-architecture-birth-packet.md.

The envelope word is still the tell. A block opening `CONVERSATION:` that arrives in Claude Code is a chat kickoff at the wrong door, and a block opening `SESSION:` that arrives in a chat is a worker dispatch at the wrong door. Name which it is when refusing, so the correction is one paste, not a conversation.

The first-contact question in the pin skill, section 0, is unaffected. It exists for blocks that name nothing. A block that names everything gets an envelope check and, if this is the wrong door, a refusal.

One narrow exception, and only this one. A surface may continue work when it IS the named destination and only a non-identity detail is wrong, a stale surface label on a block that correctly names this room and table. When Claude discovers a lane is genuinely living on a different surface than planned, it says so once, updates the lane ledger row to record the real surface, and the lane continues where it actually lives. Nobody re-pastes a lane to move it unless Allison asks. That is a surface correction inside a correct identity, never adoption of an identity from another door.

## Naming

Claude proposes the conversation name: short, the topic, and readable in a sidebar (e.g. `Ember Audit`, `EPIC Funnel Audit`). Keep it to the words that identify the lane; date suffixes and the word "kickoff" no longer ride on the name itself under v1.2, because the name is now the line the auto-titler reads. When a lane is genuinely date-bound, the date goes in the block body, not in the name.

The name in the kickoff block IS the table's name for life, it is what the receiving chair declares as `TABLE NAME` at deliberate Table Birth (v1.6, decision 0082), and it is what the lane ledger records. The chair's visible title must read exactly that name for the chair's life (v1.8, decision 0088), compared at Birth and repaired again at Rejoin, at Reseat, and whenever drift is actually observed or reported, by the surface itself where it can read and set its title and by Allison, handed the exact title, where only she can. Never on a schedule and never unprompted. A manual visible-title rename alone, Allison's own included, never changes the TABLE NAME, the table's identity, or what the ledger records. A differing title is drift and is repaired back to the exact TABLE NAME. A genuinely different durable mission gets a different table by deliberate Birth, never by renaming a sidebar title (decision 0088).

Worker (Code session) names are a different rule with a different format, `<Table Name> - <Specific Job>`, self-titled at birth through the native session-management tool (decision 0074). See the pin skill, section 5, and code-block-routing, Session Naming. Do not apply the worker format to a table name, and do not put a room prefix on either by default. The two titles are the two roles (decision 0088). A chair reads exactly the TABLE NAME and never carries a job suffix, a worker always carries one and never reads as the bare table name, and no dispatch, wrap, or steward action ever retitles the home chair to a worker's job.

## Ordering when Allison asks mid-detour

If a Code block already shipped before the new lane existed (the detour escalated), the kickoff block ships next, homed correctly, and it must name the already-running Code session so the carry-back address is unambiguous. Fix the home at the first opportunity; never let a worker session carry back to a lane that does not exist.

## Rules

- The origin lane records the spawn as a waiting-on item; the pin skill handles the paste confirmations on each surface as usual.
- Findings that change origin-lane decisions travel back as a short paste Allison carries, never assumed to be known cross-lane.
- Every paste carries the envelope (v1.1). A receiving surface that is not the block's named destination inspects it, refuses it, and states the correct routing, and never adopts the inbound identity (v1.6, decision 0081).
- A chat kickoff opens with the bare conversation name; a chat block heads its envelope CONVERSATION, never SESSION; a chat never gets a routine or unprompted rename instruction (v1.2), and a drift-driven chair title repair under v1.8 is not one.
- The Code half of a spawn pair carries its WORKTREE line; a spawning Code block without one is malformed and bounces home (v1.3).
- A table is named exactly once, at deliberate Table Birth: declared as ROOM plus TABLE NAME (v1.5, decision 0077, trigger amended by decision 0082), and its chair's visible title is kept exactly equal to that name for the chair's life, self-maintained where the surface can read and set its title, otherwise handed to Allison as the exact title at Birth, Rejoin, Reseat, and on observed or reported drift (v1.8, decision 0088).
