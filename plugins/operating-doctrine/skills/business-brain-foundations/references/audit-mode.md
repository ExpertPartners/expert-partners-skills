Audit the selected brain as it exists. Write a report, not corrections. This mode extends Foundations because the same live master, evidence, version rules and brain boundaries govern both filling and checking.

## 3. Compare versions and evidence

Read candidate bodies before calling them duplicates or selecting a version. Record each candidate's link, version/date, owner, role and substantive differences. Prefer the most complete and most recent only when the same authoritative candidate satisfies both. If the newest is thinner, report both and the unresolved choice. Never merge, delete, archive or rewrite candidates during an audit.

Every duplicate or conflict claim needs a paired evidence row: file A ID/link/version and a short body excerpt or exact section, file B ID/link/version and its excerpt or exact section, plus why the content overlaps or contradicts in the same role/scope. A repeated title, listing, count or timestamp alone cannot support the claim. Without both IDs and evidence for each, label it UNVERIFIED, do not count it as a confirmed finding, and name the missing read. Blank masters, ready-to-fill copies, filled drafts and historical exports have distinct roles and are not automatically duplicates. Apply this requirement to duplicate arrival claims too, using stable source and destination IDs and receipt/content evidence.

Anyone-with-link reader visibility is an informational sharing fact only. Allison preserves link-reader sharing. Do not score it as deficient, elevate its priority because of a folder title such as Private, recommend removing it, or change permissions. A separately evidenced anyone-with-link editor grant is a different fact; do not infer it from viewer access.

Check whether essential evidence is held and usable, such as actual past proposals, sales calls, customer questions, attributed testimonials and authentic case outcomes. Report unavailable or unadmitted evidence as a gap, not a negative business fact. Recommend specific missing references and their owning department. Do not start recording intake, external research or a recovery hunt as part of checking the brain.

Apply the Launch Points arrival health check, not just a successful-read test. Identify the existing authorized recording/file arrival register and its configured window or checkpoint. Compare the expected source records with the actual owning-brain arrivals by stable source identity, not totals alone. Report the window, expected count, matched count, missing IDs, duplicates and failed/delayed routes, with source and destination evidence. Read matched content or its verified receipt to distinguish an empty shell from a usable arrival. Preserve selective sharing: private recordings not admitted to the company brain are not missing company files.

Cal's demonstration checks the 100 most recent source transcripts against local files after a sync failure. That is a demonstrated check window, not an invented universal quota. Use the owning route's actual expected set; if a smaller sample is all that can be checked, disclose it and never infer full coverage. Without an accessible expected-source register or destination inventory, mark arrival reconciliation unverified and name the exact missing evidence. Do not claim zero missing from a destination-only listing.

The existing daily health-check owner owns scheduling and founder alerts under current decisions. An on-demand audit records arrival findings and routes them through the existing owner/handoff. It does not install another monitor, send alerts, ingest files or repair syncs merely because it found a problem.

Prioritize findings:

- P1: conflicting operative instructions or commercial facts that can drive a wrong action, or verified cross-brain/private-audience leakage.
- P2: missing baseline pieces, blank/thin required content, unsupported claims, stale authoritative content and unresolved version selection.
- P3: naming, routing or review hygiene without a demonstrated higher-impact effect.

These are report priorities, not permission to fix. Resolve business-policy choices before recommending mechanical wording changes. Assign the owning brain/department and the next correction run, with evidence and a concrete proposed action, not an invented owner decision.

## 4. Save the report

Use the current document-formatting and naming standards. Save a Google Doc in the selected owning brain's Operations folder. Announce the exact destination and name in one line, then save. Search that destination for an existing report on the same brain/department and subject before creating anything. Update that Google Doc in place under a revision guard, retaining its identity and ordinary version label. Keep run dates and findings clearly distinguished, with prior observations preserved through document history or dated sections, not presented as current evidence. Create a separate report only for a genuinely different scope or purpose.

Treat saving as a recoverable transaction, not a best-effort upload. Atomic means one complete content commit, with no partially replaced report treated as complete; Drive and the recovery record are not a single database transaction.

1. Before any report write, persist a `SAVE_PENDING` entry under a revision guard in the existing authorized task/handoff, not a new tracker. Include run ID, scope, exact title/parent, target report ID if known, expected revision, complete report payload (or a durable authorized payload reference and hash), before snapshot and status. Read the checkpoint back. If it cannot be persisted, report SAVE_BLOCKED and do not claim delivery. A local scratch file or chat promise alone is not recovery storage.
2. Commit the complete report in one supported atomic request. For an existing Google Doc, read its current revision and use Docs batchUpdate requiredRevisionId for the whole content replacement. Never clear then insert in separate calls. If the connector cannot enforce a revision guard, use the authorized Docs API route instead. On a revision mismatch, re-read, reconcile and retry without overwriting another writer. For creation use a supported idempotent create when available; otherwise create one empty shell, record its returned ID durably before adding content, then commit content in one guarded batch. An empty shell is SAVE_PENDING, never a filed report.
3. Persist the returned target ID and revision as soon as known. Cancellation, timeout, interruption, tool error or ambiguous response leaves SAVE_PENDING (or SAVE_FAILED with the exact reason), never COMPLETE. On the next invocation, read pending entries and search the exact destination/title and run marker before any new create. If the prior call actually committed, read and verify that target; otherwise resume the same target and payload under a fresh revision guard. If the shell ID was lost, search and inspect candidates, do not blindly create another. Multiple indistinguishable candidates remain a reported recovery ambiguity, not an unsupported duplicate finding.
4. Read the filed Google Doc back in full, verify parent, exact title, run marker and complete report content against the checkpoint. Verify formatting and record the revision and content hash. Then take the after snapshot and compare with before. File the snapshot result in the same report in one guarded batch and read back that final version too. Scope the unchanged statement to the recorded snapshot interval; do not imply an everlasting guarantee. Only after verified readback persist `SAVE_COMPLETE` with report link, revision, hash and snapshot verdict. A crash after readback but before checkpoint completion is resolved by that same readback on the next run.
5. For a legacy cancelled run with no checkpoint, use its existing task/handoff/session evidence to identify the intended save, record the missing checkpoint and search the intended destination. Resume recoverable content; otherwise report the lost payload explicitly and carry out a clearly labeled replacement audit in the same scope. Never silently discard the earlier failure or present a replacement as recovery of the original bytes.

No cancellation is swallowed. Finish through authorized alternative routes without asking for routine retry approval. If access or another genuine blocker prevents recovery, preserve the payload and SAVE_FAILED/PENDING status in the existing record and report the exact blocker and next recovery action. The run is not finished until its filed report is read back. These are delivery correctness checks, not human approval gates.

Report structure:

1. Title, run ID/time, brain, department and `REPORT ONLY. Not an acceptance certificate.` Add `Source files unchanged within the recorded snapshot interval` only with a passing before/after comparison.
2. Summary of checked scope and outcome. Report structural coverage separately from content health, with explicit denominators and unread/inaccessible counts. Partial coverage never becomes a clean brain verdict.
3. Master and source manifest, exact links, versions, read time, coverage, exclusions and access gaps. Label the selected copy's role, such as ready-to-fill, so a blank copy is not mistaken for a failed production brain.
4. Nineteen-piece matrix with all dimensions above, source links and specific field-level gaps. Add applicable Compliance and explicitly included department support separately.
5. Naming/home findings, stale claims, cross-file contradictions and competing versions, each with evidence or a clear unverified label. No findings in checked scope does not mean none exist elsewhere.
6. Missing references, Launch Points expected-versus-arrived reconciliation and instruction health, separating filed content from live runtime configuration.
7. Prioritized owner correction plan. No source edits occurred; fixes need a separate owner's run. Audit invocation alone never starts that run.
8. Provenance and gaps, including any missing teaching or readiness crosswalk, save/recovery status and readback receipt, before/after source snapshots with comparison results, then the saved report link in the handoff.

Return the exact report name as a Markdown hyperlink, material gaps and the actual snapshot verdict. Never assert unchanged without proof. Run the [Bench regression checklist](audit-regression-checklist.md) after audit-mode changes. A proof audit and repository checks demonstrate delivery, not independent acceptance. Where Company Test Bench owns acceptance, leave that verdict to the Bench through the existing orchestrator.
