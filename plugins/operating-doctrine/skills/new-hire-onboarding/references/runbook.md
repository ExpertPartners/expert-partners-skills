# Onboarding connector runbook

## Person

Use Drive by named user, only for the hiring company's current Company Core and the hire's department folder, never an entire shared drive, link share, group or another Core. Use `get_file` to confirm each exact folder ID, folder MIME type, `trashed=false` and `capabilities.canShare`. Use `list_permissions` with `supportsAllDrives=true`, all pages, including `id,type,emailAddress,role,deleted,expirationTime`. Normalize connector field names. Provide `kind:"person"`, `mode:"plan"` (read-only) or `"apply"` (authorized named assignment only), `principal` (exact email), and `folders`, in Core-then-department order. Each folder has `id`, `verified` (live metadata matches the approved location), `can_share`, `complete` (all ACL pages verified) and `permissions` (only matching named user ACLs, each with `type`, `email`, `role`, `id`, `deleted`, `expires`). Deduplicate the two folder IDs if the approved map identifies the same folder for both.

Normalize omitted Drive `deleted` as false when listing succeeded and no deletion is indicated. Make no writes if any row is blocked. An existing higher role is recorded, not changed. Expiring or otherwise ambiguous matching ACLs are not a durable grant and are not overwritten; resolve through the existing access owner. For already verified durable group or inherited access, set `effective_access_verified:true` only after verifying the underlying entitlement and reading the exact folder on the hire's own connection. This avoids an unnecessary direct grant. An ACL match or folder read is not the hire's first-use proof.

In apply mode, for each `status:"create"` row only, use Drive `create_permission` with exact `file_id`, `type:"user"`, `role:"reader"`, exact email, `supports_all_drives:true`, `send_notification_email:false`, and no other grant option. Serialize applies per principal/folder. Refresh that folder's ACL immediately before writing. After a successful grant or an uncertain response, reread the ACL before another attempt; no blind retry. Stop further writes if a row cannot be verified, retain the completed rows, and resume by replanning from live ACLs. Never remove an existing permission to roll back. In the final snapshot with all rows present, set `first_use:true` only when the hire has opened the non-sensitive sample and its title and parent were verified. Otherwise record access verified, first use outstanding. The skill must not use the operator's own read as proof.

## AI employee

Read the gateway's current deployed account/profile and scope route. The existing gateway has read tools, not a provisioning endpoint. Reuse the mapped identity/profile and its existing setup route. On the Hub rail, use the supported fixed department credential tied to the assigned profile, with secret storage and deployment handled by the existing gateway owner. On the MCP rail, use a distinct supported sign-in mapped to the department when available. Do not substitute the Hub leader credential or a leader MCP session. A narrowed leader read can diagnose a rollout gap but cannot prove the hire's access. If the named identity or profile has not been provisioned, send the assigned identity and exact scope gap through the existing gateway owner route, then verify the deployed result. Do not mint a credential yourself, add a shadow permission store or launch a general scope rollout. No credential or hash goes in the receipt.

Get the approved Core scope-to-folder map from the live map and current ruling (one canonical Core per brain; do not derive it by matching every `-core` suffix while a merge is underway). Get the assigned department scope and preexisting approved extras from the owning deployed profile. No unrelated private scopes or wholesale cross-department grants. On the hire's own authenticated connection, call `list_scopes` and verify returned scope/folder IDs. Use `discover` to verify every required root and `read` all pages of a non-sensitive Core or department sample belonging to the first task. Test denial with a scope outside the approved profile using a metadata-only `discover`; don't retrieve unrelated documents. In plan mode compare the proposed scope mapping only, without claiming a hire was tested.

Supply `kind:"ai"`, `mode`, `own_core` (scope key), `cores` (approved scope-to-folder mapping for all current company Cores), `department` (scope key), `department_folder`, `extras` (approved runtime scope-to-folder mapping for existing entitlements, may be empty), and `observed` (scope-to-folder mapping from the actual principal, or `{}` if unprovisioned). For `mode:"apply"`, set `principal_verified` only when first-party runtime binding proves this is the named hire, `roots_verified` only when every required root discovered successfully under that same binding, `instructions_verified` only after the instructions were saved and read back from the target project, `first_use` only after the target runtime used the whole sample from the correct scope for the first task, and `recovery_verified` only after the target runtime demonstrates scope denial and authorized recovery from missing evidence. A checker input is a control record, not proof of its own truth. Missing, unexpected or misrouted scopes block completion. Route a missing Core or a stale split Core to the existing rollout owner; never change another employee's access.

Install this pointer at the top of the target project's knowledge instructions, preserving existing role, voice and write boundaries. Don't append a duplicate if already present.

> Read company knowledge first for every task that depends on company facts, rules, decisions or methods. Start with the live HQ Rulebook and applicable current Decision Log when governance matters, then your own company Core, then your department and any other authorized company Core relevant to the task. Use the Brain Gateway, follow all pages with the same file version and verify the scope and parent. Never copy company knowledge into instructions or substitute unrelated or private material. Recover through authorized routes and report any unresolved gaps before relying on missing facts.

## Receipt

Include the authorization source, assignment, date and owner, exact folder/scope links, already present or granted/verified results, the sample title with its verified parent, named runtime proof where applicable, and any incomplete step with its existing owner. Use `planned`, `blocked`, `access_verified` or `complete` as the run state. No mutation, not run or delegated is not complete. See the output of the helper for affected rows or checks; do not include raw ACLs, tokens, or unrelated principals.
