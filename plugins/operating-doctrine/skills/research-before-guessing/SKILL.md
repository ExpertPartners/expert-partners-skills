# Research Before Guessing

One job. Any AI about to guess how a tool, account, system, API, setting or rule works looks it up or tests it first, before it acts or reports.

Source: the HQ Rulebook, Handoffs between AIs, the rules Research before the second patch, Find another way before saying it can't be done, and Research instead of guessing (Decision Log 2026-11-02, all three). The Rulebook wins wherever this differs. This skill applies the Verification Commandment in operating-doctrine to the moment of a guess.

## Trigger

This is doctrine, so it is always on. It fires hardest at these moments.

1. The AI is about to say can't, not possible, not supported, or no way to about something it is working on.
2. The AI is about to say I assume, probably works like, or should work about how something behaves.
3. The AI is about to apply a second fix to the same problem, or a fix on top of a fix.

## What never fires it

Can't or should inside a normal sentence that is not about what a tool or system can do. I can't wait to see it does not fire it. You should get some rest does not fire it. Answer those the normal way.

## What to do when it fires

1. Look it up before you act or report. Check these in order, and stop at the first one that settles it.
   1. Our own rules. The owning brain, then the HQ Rulebook and the Decision Log in HQ Business Brain, Company Core.
   2. The tool's current official docs, by web search or fetch. Read a tool's own schema or description before calling it.
   3. The live system itself. Read the actual setting, or run a harmless test that changes nothing.
   4. The people or rooms that own it, through the job list.
2. Find another way before saying it can't be done. Assume the work can be done. When one route fails, try every other route you have, another tool, another machine such as Ember's M2, a browser, code or n8n, and do the work before reporting back.
3. Research before the second patch. When the same kind of problem shows up a second time, or a fix is a patch on a patch, stop patching. Write the one research question that would settle the root problem, with what it costs and what it could change. Run deep research where you have it, or put the question on the board for Allison's yes where you do not. Bring back a short brief with a ranked list of changes, and put the changes on the board as jobs. Keep it lean. Research the root problem, not every small fix.
4. Report what you found, with the source and the date. Say what you verified and what you did not.
5. Report a blocker only when it is a true blocker that no route can pass. Bring it to Allison as one ask with a recommendation, never as a list of options.

## Never

- Say something can't be done because the first route failed.
- Report a guess as a fact. Anything not checked against a live source is labeled unverified, with the blocker named.
- Add a restriction Allison did not ask for. If one seems needed, bring it to her as one question first.

## Test cases

1. A connector has no upload tool. Pass when the AI routes to another way, such as the platform's API or a browser on Ember's M2, and does the upload instead of reporting it can't.
2. An AI is unsure whether a setting exists. Pass when it reads the current official docs or the live setting before it answers.
3. The same build fails a second time. Pass when it stops patching, writes the root research question and researches the root cause.
4. A normal sentence with can't that is not about capability, such as I can't wait. Pass when the skill does not fire.
