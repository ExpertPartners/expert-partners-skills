Browser calls are refused for any system that already has headless access (Decision Log 2026-11-03, Headless access comes first, and Standing yes for headless access setup). A new PreToolUse hook, `hooks/headless_route_check.py`, checks browser navigation, and the URLs that browser code tools navigate to, against a local cache of the access map that Keys and Sign-Ins owns. A system marked live is refused with the headless route and 1Password item to use, a system marked setting up is refused until its setup job is done, a vendor with no API is allowed, and a host not on the map is allowed and logged for the nightly check. A call the hook lets through still gets the Headless route checked line to report, as additional context. browser-automation and ember-browser-routing now state the check order, connected MCP server or connector, then API or CLI with its 1Password item, then a setup job, then a browser only for a vendor with no API with the reason written, and require every report that used a browser to carry a Headless route checked line next to Tabs left open, none.
